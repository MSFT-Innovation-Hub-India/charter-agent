# Consolidation rules — SOW Response

How the generic `consolidate` skill assembles the final SOW Word document, with SOW-specific section ordering, formatting, and reconciliation checks.

## Section order (default)

```
1. Executive summary           (generated by consolidate from technical + commercial)
2. Technical scope             (from technical-scope task submission)
3. Project management scope    (from pm-scope task submission)
4. Commercial                  (from commercial task submission)
5. Case studies & testimonials (from case-studies task — RAG output)
6. Annexes                     (only if the RFP requested any; pulled from collaborator submissions)
```

Override only if the RFP's required SOW structure is different. Put the override in the Charter's `consolidation_rules.section_order[]` at charter time, not at consolidate time.

## Template

If the customer's RFP mandates a specific SOW template ("respond using the attached template"), the `consolidate` skill should honour it — fetch the attachment, use its styles, headers, footers, section headings, and numbering. Otherwise build the Word document from scratch using a clean default layout (1" margins, single-column, Heading 1 per section, embedded TOC).

Do **not** pre-commit a template path at charter time and do **not** create any shared folder, OneDrive file, or SharePoint location for collaborators. Collaborators reply on whatever surface suits them (inline email, attached Word doc, OneDrive link, Teams reply); the SOW Owner's inbox + the project's Teams chat are the canonical capture surfaces (see `references/COMMUNICATION_MATRIX.md`).

## Cross-section reconciliation

The `consolidate` skill must run all `consolidation_rules.cross_section_checks[]` and report failures as `findings[]` (kind `gap`) on `state.consolidation.findings`. The standard SOW set:

1. **Effort reconciliation** — sum of effort hours in commercial section equals sum of effort hours in the PM scope WBS, per role and per phase. Tolerance: zero. If they differ, the gap names both totals.
2. **Component coverage** — every component named in the technical scope appears in (a) the PM scope WBS and (b) the commercial pricing breakdown. Missing entries are reported by name.
3. **Milestone consistency** — every milestone in the commercial payment schedule corresponds to a deliverable named in either the technical or the PM scope.

Findings are surfaced to the SOW Owner in the dashboard. The Owner decides whether to ask the offending collaborator for a revision (`SuggestedAction.kind = "clarify_gap"`) or to override.

## What consolidation does NOT do

- It does not silently fix numerical mismatches. Gaps are reported; never auto-corrected.
- It does not infer missing sections. A missing section is a `gap` finding, not a generated placeholder.
- It does not redact case-study customer names. NDA handling is the responsibility of the SOW Owner; the case-studies submission is consumed verbatim.
- It does not pre-create shared folders, templates, or upload locations at kickoff time. The deliverable is assembled at consolidation time and either stored in the SOW Owner's OneDrive or emailed back to them for review — the SOW Owner decides where it ultimately lands.
